Async-RBench

面向大语言模型智能体的异步任务执行测评Benchmarking Asynchronous Task Execution in LLM Agents

我们评测智能体如何根据新到达的结果调整正在执行的任务。We evaluate how agents revise ongoing work when new results arrive.

异步场景Async scenarios

八个场景各 25 个任务，每个任务按一个主场景计数。公开目录只提供总体分布，不披露逐任务的私有事件标注。Each of the eight scenarios contains 25 tasks, with each task counted once under its primary scenario. Only aggregate counts are public; per-task event labels remain private.

保持幂等，避免重复操作和不必要的重建。Remain idempotent; avoid repeated side effects and needless rebuilding.
区分临时证据与完整结果，验证整合后的状态。Distinguish provisional from complete evidence and verify integration.
恢复失败的子任务，同时保留其他有效进展。Recover the failed subtask while preserving valid progress elsewhere.
调整任务范围和依赖，并重新检查受影响的工作。Revise scope and dependencies, then recheck affected work.
权衡等待、取消与调度，保护已完成的工作。Balance waiting, cancellation and scheduling while protecting completed work.

Partial trials may have null headline metrics because coverage is incomplete. Read episode results and coverage; do not treat null as zero.

DRS 和成功率各测什么？What do DRS and success measure?

DRS 检查新结果之后的必要修改、有效工作保留、禁止行为和重新验证，并结合事件最终结果。成功率只统计完整任务目标全部通过的运行；两者分别报告。DRS checks required changes, retained work, forbidden effects and verification after a new result, together with the event outcome. Success counts runs that pass all task goals. They are reported separately.

汇总与审计分别检查什么？What do aggregation and audit check?

上面的 aggregate 命令显式绑定 first-manifest.json，检查计划覆盖。audit-run 检查契约、产物和版本；它只自动寻找 runs/manifest.json，不绑定本例的 first-manifest.json，因此通常显示 manifest_complete: null。计划是否完整，以显式绑定 manifest 的汇总报告为准；不要用无绑定的审计结果替代覆盖检查。The aggregate command explicitly binds first-manifest.json and checks plan coverage. audit-run checks contracts, artifacts and versions, but only auto-discovers runs/manifest.json, not this example’s first-manifest.json. Its manifest_complete is therefore normally null. Use the manifest-bound aggregate report for coverage, not an unbound audit.
