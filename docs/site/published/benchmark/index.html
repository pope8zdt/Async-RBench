Async-RBench

Benchmarking Asynchronous Task Execution in LLM Agents

Async-RBench evaluates how large language model (LLM) agents revise ongoing work as asynchronous results arrive.评测智能体在新结果陆续到达时，如何调整正在执行的任务。

Abstract

Large language model (LLM) agents increasingly execute tasks asynchronously: a main agent continues working while its subagents run, and the task state may change before their results arrive. The main agent must decide which work to update or preserve and which checks to repeat, while avoiding prohibited changes. Final task success alone does not reveal whether these results were handled correctly, and natural asynchronous arrivals are hard to reproduce. We introduce Async-RBench, a benchmark for asynchronous task execution in LLM agents, with 200 executable tasks covering eight scenarios. A scenario controller regulates result delivery using predefined task-state conditions, while an Event Response Contract (ERC) specifies what each response must change, preserve, avoid, and re-verify. The Dynamic Replanning Score (DRS) weights the response process and outcome equally and is reported separately from task success. We evaluate nine agents and find DRS scores of 19.2–45.1, with the lowest scores on duplicate reports and subagent failures. Under our execution protocol, all nine agents obtain lower task success with asynchronous than with batched delivery (26.0% vs. 29.7% on average). For three agents, prompting the main agent to rebuild its plan after every result improves DRS by only 2.6–3.5 points. Together, these findings highlight the challenges of reliable asynchronous task execution and the need to evaluate how agents handle incoming results alongside end-to-end task success.

Evaluation Framework评测框架

About the framework框架说明

The configuration selects the model, task and execution limits. A main agent delegates work to concurrent subagents in isolated workspaces. The scenario controller checks submissions and holds results until task-specific release conditions are met, with a maximum-wait fallback. A result counts as presented only when it enters a main-agent request. In Async mode, the main agent can continue working while subagents run; in Batched mode, it waits for the batch of results. The benchmark tests whether an agent can revise affected work, preserve valid progress and check the revised result—not just whether it eventually finishes.配置指定模型、任务和运行限制。主代理把工作分派给在隔离工作区中并发运行的子代理，场景控制器检查提交，并按任务规定的释放条件缓冲结果，等待超时则回退释放。只有结果实际进入主代理请求时，才算被呈现。Async（异步）模式允许主代理在子代理运行时继续工作；Batched（批处理）模式则等待一批结果。评测关注智能体能否修改受影响的工作、保留有效进展并验证修改后的结果，而不仅是最终能否完成任务。

For each target event, a private Event Response Contract (ERC) specifies what must change (C), what must be preserved (R), what is forbidden (F), what must be verified (V), and the required event outcome (O). An external evaluator checks recorded actions and artifact states from the event’s presentation to the main agent until the run ends. The process score P averages the applicable C, R, F and V components. Q scores the outcome requirements O against the final state; P and Q each range from 0 to 1. The event-level Dynamic Replanning Score (DRS) combines them with equal weight on a 0–100 scale. A run’s DRS averages its scored target events; this collection has one target event per task. Required events missed because the agent stops early receive zero. These contracts specify obligations, not a single required action sequence. The illustrations show possible responses, not recorded agent behavior.每个目标事件都有私有的 Event Response Contract（ERC，事件响应契约），规定必须修改的内容（C）、必须保留的状态（R）、禁止的行为（F）、必须执行的验证（V），以及事件要求的最终结果（O）。外部评估器检查从事件实际呈现给主代理到运行结束之间的动作和产物状态。过程分数 P 是适用的 C、R、F、V 分量的均值；结果分数 Q 衡量最终状态满足要求 O 的程度。P 与 Q 均在 0–1 范围内。事件级 Dynamic Replanning Score（DRS，动态重规划分数）将两者等权合并，范围为 0–100。一次运行的 DRS 是其被评分目标事件的均值，本任务集每个任务有一个目标事件；因智能体提前终止而未到达的必需事件记为零分。契约规定要履行的要求，并不规定唯一动作序列。图中插画展示可能的应对方式，不代表真实运行表现。

Event DRS事件 DRS = 100 × (P + Q) / 2

Task success (S) is measured separately: a run succeeds only if all required final task checks pass. The leaderboard reports the percentage of successful runs for both modes. Task success is not included in DRS; DRS is reported only for Async runs.任务成功指标（S）独立计算：只有所有规定的最终任务检查均通过，单次运行才记为成功。榜单分别报告两种模式的成功率。任务成功率不计入 DRS；DRS 仅用于 Async 运行。

Sources and task design数据来源与任务设计

Async-RBench adapts task objectives and environments from five benchmarks, with 40 tasks from each. These are adapted tasks, not the original benchmarks’ test sets. Each task has one primary asynchronous scenario; the eight scenarios contain 25 tasks each. The collection has 621 initial subtasks.Async-RBench 基于五个基准中的任务目标与环境进行改编，每个来源各 40 个任务，并非直接使用原基准的测试集。每个任务按一个主要异步场景计数，八类场景各 25 个任务，共包含 621 个初始子任务。

LLM-assisted screening identifies tasks where a subagent result could change an earlier decision. Researchers design and review the parallel work, event timing and response requirements. Trial runs, reference solutions, equivalent implementations and invalid variants check task solvability and evaluation behavior. Per-task scenario labels and detailed evaluation requirements remain private.先由大模型辅助筛选子代理结果可能改变已有决策的任务，再由研究者设计、标注并复核并行工作、事件时机与响应要求。试运行、参考解、等价实现和无效变体用于检查任务可解性与评测行为。逐任务的场景标签和详细评测要求不对参评者公开。

Additional experiments补充实验

Native lets the main agent decide whether and how to revise its plan. Oracle is a reference recovery program with knowledge of the event requirements, not a capability-matched baseline. Frozen uses a continuation generated by the same model without the target result. Full-rebuild instructs the agent to reconstruct the remaining plan after each subagent result is presented, while retaining completed work. These three-agent comparisons are separate from the main experiment.Native 由主代理自行决定是否以及如何调整计划。Oracle 是知晓事件要求的参考恢复程序，不是能力匹配的基线；Frozen 使用同一模型在看不到目标结果时生成的后续动作。Full-rebuild 要求智能体在每次子代理结果呈现后重建剩余计划，同时保留已完成工作。这些三模型对照独立于主实验。
