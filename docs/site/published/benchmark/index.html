Async-RBench

Benchmarking Asynchronous Task Execution in LLM Agents

Async-RBench evaluates how agents adapt ongoing work as new results arrive.评测智能体在新结果陆续到达时，如何调整正在执行的任务。

Abstract

Large language model (LLM) agents increasingly execute tasks asynchronously: a main agent continues working while its subagents run, and the task state may change before their results arrive. The main agent must decide which work to update or preserve and which checks to repeat, while avoiding prohibited changes. Final task success alone does not reveal whether these results were handled correctly, and natural asynchronous arrivals are hard to reproduce. We introduce Async-RBench, a benchmark for asynchronous task execution in LLM agents, with 200 executable tasks covering eight scenarios. A scenario controller regulates result delivery using predefined task-state conditions, while an Event Response Contract (ERC) specifies what each response must change, preserve, avoid, and re-verify. The Dynamic Replanning Score (DRS) weights the response process and outcome equally and is reported separately from task success. We evaluate nine agents and find DRS scores of 19.2–45.1, with the lowest scores on duplicate reports and subagent failures. Under our execution protocol, all nine agents obtain lower task success with asynchronous than with batched delivery (26.0% vs. 29.7% on average). For three agents, prompting the main agent to rebuild its plan after every result improves DRS by only 2.6–3.5 points. Together, these findings highlight the challenges of reliable asynchronous task execution and the need to evaluate how agents handle incoming results alongside end-to-end task success.

Evaluation framework评测框架

About the framework框架说明

The configuration sets the model, task and execution limits. The main agent delegates parallel work to subagents in isolated workspaces and continues working while they run. A scenario controller releases their results under predefined conditions. The main agent must then update affected work, preserve valid progress and verify its changes. The runtime records actions and artifact states. An external evaluator checks this evidence against a private Event Response Contract (ERC), reporting the Dynamic Replanning Score (DRS) separately from final task success.配置指定模型、任务和运行限制。主代理将并行工作分派给隔离工作区中的子代理，并在它们运行时继续执行任务。场景控制器按预设条件交付结果；主代理需要据此修改受影响的工作、保留有效进展并验证修改。运行框架记录动作和产物状态，外部评估器依据私有的事件响应契约（Event Response Contract，ERC）检查这些证据，分别报告动态重规划分数（Dynamic Replanning Score，DRS）和最终任务成功情况。

Leaderboard榜单

The paper evaluates nine agents on the same 200 tasks, with three repetitions per task for both asynchronous (Async) and batched (Batched) result delivery. DRS measures an agent’s ability to replan under asynchronous interruptions, accounting for both the response process and the event outcome. S is the end-to-end task success rate. Higher is better for both.论文在相同的 200 个任务上评测九个智能体，分别采用异步（Async）和批量（Batched）结果交付，每个任务各重复三次。DRS 衡量智能体在异步中断下的动态重规划能力，综合考察响应过程及事件结果；S 是端到端任务成功率，两者均越高越好。

Paper results: Dynamic Replanning Score and task success
#AgentDRSS · Async %S · Batched %ΔS · ppCalls

The eight scores below each agent are scenario-level DRS values, not additional metrics. For each scenario, we average its 25 task scores within each repetition, then report the mean ± sample standard deviation across the three repetitions. Overall DRS is the equal-weight mean of the eight scenario means.每个智能体下方的八项分数是八类场景各自的 DRS，而非额外指标。每类场景先在每次重复内对 25 个任务的分数求均值，再报告三次重复的均值 ± 样本标准差。总 DRS 是八类场景均值的等权平均。

ΔS is the Async task success rate minus the Batched task success rate, in percentage points (pp), calculated before rounding. Calls is the mean number of model responses per Async run, summed over the main agent and all subagents. These values come from the paper; community submissions do not change this table.ΔS 是 Async 任务成功率减去 Batched 任务成功率，单位为百分点（pp），在四舍五入前计算。Calls 先合计每次 Async 运行中主代理和所有子代理的模型响应次数，再对运行取平均。数值来自论文，社区提交不会改变此表。

Additional experiments补充实验

Native lets the main agent decide whether and how to revise its plan. Oracle is a reference recovery program with knowledge of the event requirements, not a capability-matched baseline. Frozen uses a continuation generated by the same model without the target result. Full-rebuild instructs the main agent to rebuild its remaining plan after each subagent result is presented, while keeping completed work. These three-agent comparisons are separate from the main experiment.Native 由主代理自行决定是否以及如何调整计划。Oracle 是知晓事件要求的参考恢复程序，不是能力匹配的基线；Frozen 使用同一模型在看不到目标结果时生成的后续动作。Full-rebuild 要求主代理在每次子代理结果呈现后重建剩余计划，同时保留已完成工作。这些针对三个智能体的对照独立于主实验。
