# Async-RBench v10.1.0 Step-Bounded Termination Design

## Decision

Async-RBench v10.1.0 adopts a step-bounded, outcome-scored execution contract. A model may end an episode at any time with `finish`; the runtime never rejects that stop request. The private final verifier remains the sole authority for task success, and incomplete exposure to designed asynchronous events remains a scored dynamic failure.

Token counts are diagnostics, not normal admission gates. The four v10.0 token pools and their conservative pre-call reservations are removed. A single high, shared `emergency_total_token_cap` remains only as a runaway-cost safeguard. Triggering it produces `resource_safety_abort`, excludes the episode from official aggregation, and is never scored as model failure.

## Goals

- Use the benchmark pattern common to interactive agent evaluations: fixed interaction horizon, voluntary early stop, independent end-state evaluation.
- Remove completion feedback that tells a model which benchmark closure conditions remain unsatisfied.
- Make Linear/Async and cross-model comparisons use the same model-step and concurrency limits.
- Preserve real token usage by main/child/total as efficiency diagnostics.
- Give every termination one explicit, auditable cause.
- Ship one clean v10.1 configuration and documentation surface without active v10.0 budget-pool fields or aliases.

## Non-goals

- No task instruction, case event, registered instance, private verifier, or score denominator is changed.
- No historical v10.0 episode is migrated into v10.1.0. Old and new runs must not be mixed.
- Running v10.0 experiments and their artifacts are not stopped, edited, or deleted.
- Provider transport configuration and the existing result-submission contract are unchanged.

## Runtime contract

### Model steps

A model step is one completed provider response, regardless of how many tool calls that response contains. Official profiles use:

- `max_main_steps: 100` per episode;
- `max_child_steps: 40` per child attempt;
- `max_concurrent_children: 3`;
- `max_total_child_spawns: 5`.

When the main horizon is reached without `finish`, the episode ends with `local_status=step_limit_reached` and remains scored. When a child reaches its horizon without sealing a result, the attempt ends as `step_limit_reached` and remains an ordinary child outcome.

### Explicit and implicit stop

`finish(status, summary)` is terminal on its first execution. It does not require a current final commit, a fresh verification, an empty presentation queue, or a closed response window. The runtime records those facts at the stop boundary but does not return them to the model as missing preconditions.

A main response with no tool call is an implicit incomplete stop. A child response with no tool call is `no_submission`. The runtime does not add corrective reminder turns; this prevents benchmark-authored coaching after the model has chosen not to act.

If a response contains `finish` followed by more tool calls, `finish` is the terminal boundary and later calls in that response are not executed.

### Token safety and diagnostics

Official profiles use `emergency_total_token_cap: 20000000`. The runtime records actual provider-reported tokens after completed calls in one concurrency-safe ledger with main, child, per-actor, and total counts. It performs no worst-case token reservation and no pre/post/child pool routing.

After the first completed call that raises total actual use to or above the cap, the ledger trips once and emits `resource_safety_abort`. No later model call may start. Calls already in flight may settle and are included in the final count. The episode is unscored and leaderboard-ineligible because the safeguard prevents a comparable complete measurement.

The final runtime event is `token_usage_snapshot`; score output exposes it as `token_usage_report`. Existing `main_tokens`, `child_tokens`, and `total_tokens` remain derived independently from completed-call events.

## Scoring and diagnostics

The scorer adds:

- `termination_reason`: `explicit_finish`, `implicit_stop`, `step_limit_reached`, `resource_safety_abort`, or the existing infrastructure/timeout outcome;
- `finish_quality`: declared status plus pending-occurrence, open-window, current-final-commit, and current-verification facts captured at explicit finish;
- `step_limit_reached`: episode-level boolean;
- `resource_safety_abort`: episode-level boolean;
- `token_usage_report`: final actual-usage ledger snapshot;
- `child_step_limit_rate_per_attempt`: child attempts ending at the fixed step horizon.

The v10.0 fields `budget_exhausted`, `budget_report`, `budget_termination`, and `token_budget_exhaustion_rate_per_attempt` are removed from newly generated scores and aggregates. A premature explicit finish remains scored: `scenario_exposure_complete=false`, and the relevant dynamic opportunity/checks fail rather than becoming not-applicable.

## Configuration and compatibility

The canonical v10.1 profile fields are `max_main_steps`, `max_child_steps`, and `emergency_total_token_cap`. The removed fields are `max_main_turns`, `max_child_turns`, `max_total_tokens`, `budget_child_shared`, `budget_main_pre`, `budget_main_post`, and `budget_main_total`. There is no runtime alias or silent migration; stale profiles fail configuration loading and must be updated explicitly.

`child_context_budget_bytes` remains a context-size safety control, not a token-spend budget. Its deprecated `child_context_budget_chars` alias and the deprecated `_compress_messages` wrapper are removed.

## Repository and release scope

The release is based on current `origin/main`, including its v10 repository-surface cleanup. Runtime, protocol, scorer, aggregation, audit-facing metrics, model profiles, examples, operator documentation, package versions, and release-surface tests are updated together. Completed implementation plans and code that exist solely for the removed pool mechanism are deleted.

The release version is `10.1.0` in `pyproject.toml`, `async_rbench/__init__.py`, `async_rbench/evaluation/version.py`, `evaluation_contract.json`, README badges/headings, and release tests. The Git tag is `v10.1.0`.

## Verification

Behavior is developed test-first. Required gates are focused runtime/protocol/scoring tests, repository validation, the complete pytest suite, a clean credential scan of the staged diff, and a final diff review before commit, tag, and push.
